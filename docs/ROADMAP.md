# Antaris-Guard v0.2: the rounds

Eight rounds, each one pull request, each with an exit test that CI runs. `docs/SPEC.md` says
what v0.2 is; this file says the order. A round starts with the session's plan and the round's
questions, and the build starts after Jake answers. Where a question has a recommendation, it is
the first option, and Jake's answer in the PR thread is the record.

## What every round keeps true

- The v0.1 table passes: 107 blocked, 58 allowed, 1 unreadable, 18 subagent cases. It runs
  under `configs/inventaris.json` from R2 on, because Inventaris is the repository it was
  written for. It never shrinks; a case that moves between tables moves with Jake's yes.
- `test/compare.test.ts` passes: the frozen v0.1 hooks under `bench/versions/v0.1/` and the
  current hooks give the same decision and the same reason text (ignoring the id prefix) for
  every case in every table, except the cases the round's PR lists as new behavior.
- `node --check` on every JavaScript file. No dependency at runtime. No network in tests.
- The README changes in the same PR as the behavior. Every PR lists the rule ids it added or
  changed and the cases it added.
- No browser automation, no exceptions.

## R1: split and name

Goal: v0.1 behavior, in the v0.2 shape, with every decision carrying a rule id, plus the one rule
that cannot wait: browser automation.

Builds:

- `lib/parse.js` (the splitter, `programOf`, wrappers, shell strings, inline code),
  `lib/judge.js` (`judge(command, context)` returning `{ decision, rule, reason, parse }`), and
  `lib/rules/` with one file per rule, each exporting `{ id, name, tier, reason, test }`. The ids
  are the table in `docs/SPEC.md` section 3: G01 to G17 for the rules v0.1 has, `aws-cdk-01`,
  `aws-cdk-02` and `docker-01` for the three that will move to packs. `guard.js` becomes the
  stdin and exit-code shell around `judge()`. `subagent-guard.js` is untouched this round.
- The stderr line gains the id: `guard: blocked (G07 push-to-protected: direct push to main;
  open a PR instead): <line>`. Reason text is unchanged, word for word.
- G18 `browser-automation`, deny: a command that runs, installs or names playwright, puppeteer,
  selenium, webdriver, chromium, chrome or any browser with a headless flag, or the preinstalled
  browser path, by program, by package name under `npx`, `npm install`, `pnpm add`, `yarn add`,
  by inline code that requires or imports one, and by the `PLAYWRIGHT_BROWSERS_PATH` or
  `PUPPETEER_EXECUTABLE_PATH` variables. Searching for the word, or a commit message that
  contains it, is allowed. Twenty or more blocked cases, ten or more allowed, in
  `test/rules/g18.test.ts`.
- `bench/versions/v0.1/guard.js` and `subagent-guard.js`: byte for byte copies of the files at
  main `fdf0a2e`, frozen, with a one-line README saying so. `test/compare.test.ts` as above.
- README: a rule table with ids, names, tiers and reasons, generated by hand this round and by
  `explain --rules` from R7.

Exit test: the v0.1 table and the subagent table pass unchanged, `compare` reports zero
differences apart from G18's new cases, G18's own table passes, CI green.

Questions for Jake:

1. Test runner. (a) Move to Node's built-in `node:test`, which removes the only dependency, the
   lockfile problem and the `npm install` in CI, and makes `antaris-guard test` trivial later;
   the tables are unchanged, only `expect` becomes `assert`. (b) Keep vitest and add the
   lockfile.
2. Is `chromium` the bare program name in G18? (a) Yes: nothing a session does needs a browser
   binary, and the preinstalled one is the case that started this. (b) Only with a headless
   flag.
3. Does installing count? (a) Yes: `npm install playwright` and friends are denied, since
   installing is the first step and the diff would show it anyway. (b) Only running.

## R2: config

Goal: the lists that name a repository leave the code.

Builds:

- `lib/config.js`: loads `.claude/guard.config.json` from the project root as `docs/SPEC.md`
  section 4 defines it (`CLAUDE_PROJECT_DIR`, then the hook's `cwd`, then the process cwd),
  validates it strictly, fails closed with `G17` and the message, and returns the built-in
  defaults when there is no file. `version` is required and must be `1`.
- G01, G07, G09, G12, G13 and G16 read `blockedPrograms`, `protectedBranches`, `secretEnv`,
  `secretPaths` and `protectedPaths` from config. The word `Jake` in G16's reason becomes
  `operator`. The `rules` map can set a rule to `deny` or `off` this round (`ask` arrives in R4);
  the rules the spec marks as never off refuse `off` at validation.
- `configs/inventaris.json`: the values v0.1 has hard-coded, as the worked example. The test
  harness passes it to every table run. `configs/README.md` says what each key does.
- `bin/antaris-guard.js explain "<command>"`: prints the parse (commands, programs, piped,
  shell strings, inline code) and the decision with its rule, reading the config the hook would
  read. Not yet a package command; run as `node bin/antaris-guard.js`.
- Tests: `test/config.test.ts` covers defaults, a valid file, each kind of invalid file (unknown
  key, wrong type, a never-off rule set to off, bad version, unreadable JSON) and the lookup from
  a temporary project directory. Tables hand `judge()` the config directly.

Exit test: the v0.1 table passes under `configs/inventaris.json`. The PR lists which of its
cases come out differently under the built-in defaults (the ones that depend on Inventaris's
lists, such as `python3 -c`), which proves the config is what carries them; the three pack-bound
rules stay unconditional until R6. `compare` zero. CI green.

Questions for Jake:

1. The built-in defaults. (a) The generic set in the spec's example, with `python` and `pip`
   left out of `blockedPrograms` because most repositories need them, and the Inventaris config
   adding them back. (b) The Inventaris set as the default.
2. What a missing config means. (a) Defaults, and every log line says `config: defaults` so it is
   visible. (b) Block everything until `init` has run.

## R3: the decision log

Goal: a record the session cannot edit.

Builds:

- `lib/log.js` as `docs/SPEC.md` section 5 defines it: one JSON line per decision, allows
  included, command stored as a SHA-256 only, `prev` and `hash` chained, `genesis` first. The
  path comes from config, default `.claude/guard/log.jsonl`, created on first write. A write
  failure is a `G17` block. The subagent hook logs through the same module with `tool: Agent`.
- `verify-log` and `log` in `bin/antaris-guard.js`: verify walks the chain and names the first
  bad line; log summarizes by decision, rule, day and session, and prints the file size.
- Tests: chain correctness, a tampered line found, a deleted line found, an unwritable path
  blocking, the summary's numbers, and that no command text ever appears in the file (the test
  logs a command containing a marker string and greps the file for it).

Exit test: tables pass with logging on (to a temporary path) and off. `verify-log` passes on a
log the tests wrote and fails on the two tampered copies. CI green.

Questions for Jake:

1. The command in the log. (a) Hash only, as the spec says, so a secret on a command line never
   lands in a file. (b) The first 80 characters as well, for readability, accepting that risk.
2. Allows in the log. (a) Yes, every decision, so the chain is the whole history. (b) Only ask
   and deny, a smaller file.

## R4: ask

Goal: the third answer.

Builds:

- `judge()` returns `ask` as a decision; `guard.js` prints the hook JSON for it (stdout, exit 0)
  and still exits 2 with stderr for `deny`; `allow` stays silent. The session reads the current
  hooks reference before writing this and records in the PR what it checked.
- Config `rules` accepts `ask`. A deny rule can be moved to ask by config except the never-off
  set, which is also never-ask.
- G21 `push-to-branch`, ask by default: any `git push` that G06, G07 and G19 do not catch. G22
  `ask-program`, ask: a program in `askPrograms`.
- The test harness learns three outcomes: exit 2 is deny, exit 0 with the JSON is ask, exit 0
  with nothing is allow, and a new `ASKED` table alongside `BLOCKED` and `ALLOWED`. An allowed
  case must now be truly silent; an ask case that happened to pass as "allowed" before this
  round is caught.
- `explain` prints the three-way decision.

Exit test: the v0.1 table passes unchanged under `configs/inventaris.json`, which turns G21 off
and sets `askPrograms` to the answer below, so the five branch-push cases stay allowed. Under
the built-in defaults, the same five are ask, and the PR lists them. CI green.

Questions for Jake:

1. Default tier for a push to a branch, outside Inventaris. (a) Ask: code leaving the machine is
   the moment an operator wants to see, and a repository that pushes often turns it off in
   config, as Inventaris does. (b) Off everywhere, opt in.
2. Inventaris's `askPrograms`. (a) `["aws"]`: rare in a session, and worth a look each time;
   `gh` stays silent because every round opens a pull request with it. (b) Empty.
3. What `ask` says to the operator. (a) The rule, the reason and the command, nothing else.
   (b) Also the last three decisions from the log, for context.

What R4 became, on Jake's answers of 2026-10-19: the guard is a buffer against honest mistakes
and stays light. Claude Code's own permission settings already ask about pushes and programs, so
a second layer of prompts in the guard would only add steps; G21 and G22 are dropped, their ids
retired, and `askPrograms` is not a key. The ask answer is built and stays opt-in: no rule asks
by default, and a config can move one of the guard's own rules to ask instead of turning it off.
What `ask` says is the rule, the reason and the command (answer 3a). A deny wins over an ask on
the same line. A rule the config turns off has no effect at all, and nothing is logged for it.
The exit test that ran: the v0.1 table passes unchanged under `configs/inventaris.json`, every
allowed case silent; the ask answer is tested through the hook with a config that moves two rules
to ask. The asks that later rounds name (a missing script in R5, the packs' asks in R6) are read
against this when those rounds start.

## R5: what the command runs, and what it hides

Goal: the two known gaps, closed as far as a text judgment can close them.

Builds:

- `lib/scan.js` and G20 as `docs/SPEC.md` section 6 defines them: a script argument to an
  interpreter or a shell is read (inside the project, under `scan.maxBytes`, not a symlink out)
  and judged by the text rules (G03, G14, G18 and pack text rules once packs exist). `npm run`,
  `yarn` and `pnpm` scripts resolve through `package.json`, three levels deep. The edges from the
  spec: unreadable, too big, outside, or written on the same line is `G17`; missing is `ask`.
  `judge()` takes the file reader as part of `context`, so tests pass a fake.
- `expandVars` in `lib/parse.js` and G23: assignments on the line are substituted before
  judging; a variable the line does not define, in program or git-subcommand position, is a
  deny.
- G19 `push-to-url-or-unknown-remote`: a push whose remote is a URL or a name not in
  `config.remotes`, and `git remote add`, `remove`, `rename` and `set-url`, are denied.
- G01 judged per command, including inside shell strings, so `bash -c "curl x"` is caught by
  the program and not by luck. Any case this changes is listed.
- The programs that run a string the guard does not read yet, read the way `sh -c` is since R2:
  `find -exec sh -c`, `script -c`, `watch`, `env -S`, `parallel`, `tmux new-session`. With them,
  `$'...'` quoting, which the parser reads as a word beginning with `$`, so `bash -c $'git push
  origin main'` is not the push it is; and `git push --mirror`, which pushes every branch without
  naming one and so passes G07. Each with cases, blocked and allowed.
- Cases for all of it: twenty or more per rule, with allowed cases that look alike
  (`node scripts/copy.mjs` that copies, `npm run build`, `x=1; echo $x`, a push to `origin`).

Exit test: tables pass; `compare` lists only the new rules' cases; the scan tests run against
fixture files under `test/fixtures/scripts/` and a fake reader, never against the repository's
own files. CI green.

Questions for Jake:

1. `scan.maxBytes` default. (a) 256 KiB: every script a session writes is smaller, and a bigger
   file is `G17`, which the operator can raise in config. (b) 1 MiB.
2. A script that does not exist yet. (a) Ask, as the spec says. (b) Deny.
3. `npm run` of a script that runs another script file. (a) Follow it, three deep, the same limit
   as shell strings. (b) Judge the script line only.

## R6: packs

Goal: the rules that name a toolchain live beside that toolchain.

Builds:

- `packs/<name>/rules.js` and `packs/<name>/rules.test.ts` for `node`, `python`, `aws-cdk`,
  `terraform`, `kubernetes`, `cloud-cli` and `docker`, with the coverage in `docs/SPEC.md`
  section 8. Ids `<pack>-NN`. A pack cannot lower a core rule's tier; validation refuses a pack
  that tries.
- `aws-cdk-01`, `aws-cdk-02` and `docker-01` move from `lib/rules/` into their packs with their
  reason text intact. `configs/inventaris.json` lists `node`, `aws-cdk` and `docker`, and the
  `aws-cdk` pack reads its allowed profiles from config (`inventaris-dev` only).
- Config `packs` is validated against the packs that exist; an unknown pack name is `G17`.
- README: a packs section, one paragraph each, and the config keys each pack reads.

Exit test: the v0.1 table passes with the three rules now coming from packs; `compare` zero;
each pack's own table passes; a config naming a pack that does not exist blocks everything.
CI green.

Questions for Jake:

1. `cloud-cli` writes that are not deletes or IAM (`aws s3 cp`, `gcloud run deploy`). (a) Ask.
   (b) Deny.
2. `docker run` of an image not in the allowed list. (a) Ask. (b) Deny, with Inventaris listing
   `postgres:*`.
3. `python` pack: `pip install` outside a virtualenv. (a) Ask. (b) Deny.

## R7: the command line and the package

Goal: installable by a person in one command, verifiable in CI, and untouchable by a session.

Builds:

- `bin/antaris-guard.js` with every command in `docs/SPEC.md` section 9: `explain`, `test`,
  `init`, `upgrade`, `check`, `compare`, `log`, `verify-log` (`bench` comes in R8). `init` and
  `upgrade` refuse without a TTY on stdin and print why; G24 denies them by name and by script
  path from a session. `check` compares `.claude/hooks/antaris-guard/` to the package at the
  version in the lockfile and confirms the `.gitignore` line.
- `package.json`: `bin`, `files`, `exports` for `judge` and `parse`, `engines` node 22, version
  `0.2.0`. `npm pack --dry-run` in CI lists exactly the files that should ship. Nothing is
  published from a session; the `node` pack's own rule makes `npm publish` an ask.
- README rewritten around install: `npx antaris-guard init`, the settings block, the config, the
  commands, the rules table (now generated by `explain --rules`), the packs, what the guard does
  not catch, and the provenance line.

Exit test: `init` into a temporary repository produces a working install (the tables run against
it), `check` passes there and fails after one byte changes, `init` under no TTY refuses, G24
denies `npx antaris-guard init` and `node bin/antaris-guard.js init` in the Bash table. CI green.

## R8: the benchmark

Goal: a number per version, so the next change cannot quietly get worse.

Builds:

- `bench/corpus/<category>.json` as `docs/SPEC.md` section 10 defines it, seeded from: the v0.1
  table's blocked cases, the nineteen the comparison test found in Inventaris, the shapes every
  round added, and `legitimate.json` from the allowed table plus the commands a session runs in
  an ordinary day. Each case carries `cmd`, `expect`, `why` and `category`.
- `bench/score.js` and `antaris-guard bench [guard.js]`: runs a guard over the corpus, prints
  caught and let-through rates per category and overall, and a JSON report.
- README: the versions table with v0.1 (from the frozen copy) and v0.2, both numbers each. The
  v0.1 row is the proof the corpus is not written to flatter the current guard.
- `bench` runs in CI and fails the build if either number for the current guard drops below the
  last released row.

Exit test: the two rows exist and v0.2's caught rate is above v0.1's on every category where a
round added rules, with the let-through rate not below v0.1's. CI green.

Questions for Jake:

1. Scoring. (a) Two plain percentages, no weighting. (b) Weighted by category.
2. Who adds corpus cases. (a) Any PR, with the `why` line, and the rule that a case a released
   version passes stays forever. (b) Only with a matching rule change.

## After v0.2

- Inventaris adopts: Jake runs `init` there, the config is `configs/inventaris.json`, the
  `docs/claude/hooks` mirror and its identity test are replaced by `check` in CI, and a session's
  guard change becomes an Antaris-Guard pull request rather than a mirror edit. That is an
  Inventaris round, planned there.
- The Antaris harness takes the same three answers and the same log shape for every tool, not
  only Bash, with the operator's approval matched to the tier. The guard stays the smallest
  piece of that and keeps working on its own.
